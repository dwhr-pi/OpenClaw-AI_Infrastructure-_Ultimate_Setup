# Release v11.18.0 vorbereiten und veroeffentlichen

**Setup-Version: 11.18.** Release-Tag: `v11.18.0`. Status: vorbereitet, nicht veroeffentlicht.
Stand der oeffentlichen Release-Pruefung: 12.11.2026. Gefunden wurde nur
`v11.17.0` mit den vier Assets. Hier wurden keine Tags erstellt, Schluessel
gelesen, Signaturen erzeugt oder Releases hochgeladen.

Diese Checkliste ist **nur fuer den Maintainer**. Installationsnutzer folgen
der [Schritt-fuer-Schritt-Anleitung](../INSTALL_SIGNED_RELEASE.md).

## 1. Release-Commit freigeben

Alle vorgesehenen Aenderungen committen und pruefen lassen. Im richtigen
Repository den sauberen Arbeitsstand und den vollstaendigen Commit feststellen:

```bash
git status --short
git rev-parse HEAD
```

Bei lokalen Aenderungen stoppen. Keine privaten Dateien committen. Der
ausgewaehlte Commit muss APP_VERSION und die aktiven Katalogversionen 11.18
enthalten. CI-Fixtures sind keine Fresh-Host-, GPU-, Restore- oder Produktionsabnahme.
Offene Laufzeitgrenzen in den Release Notes nennen.

## 2. Neuen lokalen Tag erstellen

`VOLLSTAENDIGER_GEPRUEFTER_COMMIT` durch den freigegebenen 40-stelligen Hash
ersetzen. Dieser Befehl erzeugt einen Tag, noch kein GitHub-Release:

```bash
git tag v11.18.0 VOLLSTAENDIGER_GEPRUEFTER_COMMIT
git rev-parse 'refs/tags/v11.18.0^{commit}'
git show v11.18.0:setup_ultimate.sh | grep '^APP_VERSION='
```

Erwartete Version: `APP_VERSION="11.18"`. Einen bestehenden Tag nicht
ueberschreiben, verschieben oder mit Force pushen. Bei einem Fehler stoppen.

## 3. Drei noch unsignierte Dateien exportieren

Der Zielordner muss neu sein und ausserhalb des Repos liegen:

```bash
python3 -I -B scripts/security/prepare_release.py --tag v11.18.0 --output "$HOME/openclaw-release-v11.18.0"
```

Erwartet: `install.sh`, `release.json` und `SHA256SUMS`. Tag und Commit in
`release.json` mit Schritt 2 vergleichen. Nicht die alten 11.17-Dateien kopieren
und deren Versionsnamen austauschen: Installer, Commit und Signatur gehoeren zusammen.

## 4. Mit dem vorhandenen privaten Maintainer-Key signieren

Nur am eigenen sicheren Signiersystem ausfuehren. Den Pfad vorher an den
tatsaechlichen Schluessel anpassen; den Key nicht auf ein Installationsziel kopieren:

```bash
minisign -Sm "$HOME/openclaw-release-v11.18.0/SHA256SUMS" -s "$HOME/.openclaw-release-signing/release.key"
```

Jetzt muss auch `SHA256SUMS.minisig` vorhanden sein. Private Key-Datei und
Passphrase niemals hochladen, in Git aufnehmen oder in einen Chat einfuegen.
Die vorhandene Vertrauenskette kann mit demselben geprueften Key fortgesetzt
werden. Eine Key-Rotation ist eine eigene Entscheidung mit unabhaengiger Verteilung.

## 5. Lokal mit dem unabhaengigen Public Key pruefen

Im unabhaengig geprueften Checkout und mit dem passenden Public Key:

```bash
bash ./verify_release_and_install.sh --tag v11.18.0 --public-key "$HOME/.config/openclaw-trust/release.pub" --artifacts "$HOME/openclaw-release-v11.18.0" --verify-only
```

Bei Signatur- oder Pruefsummenfehler stoppen. Diese Vorpruefung startet weder
Installer noch Dienste und ersetzt nicht den echten Tag-/Installationsabgleich.

## 6. Tag pushen und neues GitHub-Release anlegen

Erst nach Review und Signaturpruefung bewusst aus dem richtigen Repository:

```bash
git push origin refs/tags/v11.18.0
```

Unter GitHub **Releases > Draft a new release** den Tag `v11.18.0` auswaehlen.
Als Titel beispielsweise `v11.18.0 - Setup 11.18`. Genau diese vier Dateien
aus dem neuen Exportordner anhaengen:

- `install.sh`
- `release.json`
- `SHA256SUMS`
- `SHA256SUMS.minisig`

Nicht `release.key`, Passphrase oder Zugangsdaten hochladen. `release.pub`
bleibt ein separat verteilter Vertrauensanker und ersetzt kein Pflicht-Asset.
Die alte Veroeffentlichung `v11.17.0` bleibt unveraendert. Erst nach abschliessender
Freigabe publizieren; "Latest" nur setzen, wenn dieses Release bewusst als aktuelles gilt.

## 7. Oeffentlichen Download gegenpruefen

Nach der Veroeffentlichung auf einem getrennten Pruefsystem:

```bash
bash ./verify_release_and_install.sh --tag v11.18.0 --public-key "$HOME/.config/openclaw-trust/release.pub" --download --verify-only
```

Erst nach erfolgreichem Download und Pruefung den Status in dieser Checkliste,
README und Installationsanleitung auf "veroeffentlicht" aktualisieren. Den
vollstaendigen geprueften Bootstrap-Commit und Public-Key-Fingerprint separat
bestaetigen, damit Erstinstallationsnutzer nicht einem ungeprueften Download vertrauen muessen.
